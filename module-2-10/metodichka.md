## 2.10.1. Зачем профиль

Время программы складывается из времени функций. `cProfile` считает, сколько раз функция вызвана и сколько времени на неё пришлось. Сначала смотрят функции с большим накопленным временем, затем решают, есть ли более простой алгоритм.

Профиль запускают на той же задаче, которую программа решает у пользователя. Замер на пустом списке ничего не говорит о рабочем объёме данных.

**Критерий 2.10.1:** в markdown одной фразой записано, чем профиль отличается от точки останова.

## 2.10.2. cProfile

Создайте `module-2-10/profile_demo.py`:

```python
def slow_sum(n: int) -> int:
    total = 0
    for i in range(n):
        total += i
    return total


def fast_sum(n: int) -> int:
    return n * (n - 1) // 2


def main():
    left = slow_sum(200_000)
    right = slow_sum(100_000)
    return left + right


if __name__ == "__main__":
    print(main())
```

Из корня курса, в активированном `.venv`:

```powershell
python -m cProfile -s cumtime module-2-10\profile_demo.py
```

`-s cumtime` сортирует таблицу по накопленному времени: сверху функции, внутри которых программа провела больше всего времени, вместе с вызовами из них.

Сохраните вывод:

```powershell
python -m cProfile -s cumtime module-2-10\profile_demo.py > module-2-10\profile.txt
```

В таблице найдите строку `slow_sum`. Колонка `ncalls` — число вызовов.

**Практика 2.10.2.** В ноутбуке запишите: сколько раз вызвана `slow_sum`, какое число напечатал скрипт, какая функция стоит в таблице выше неё.

Число на выходе — сумма `0..199999` плюс сумма `0..99999`, то есть `199999 * 200000 / 2 + 99999 * 100000 / 2`. Скрипт печатает **24999850000**.

**Критерий 2.10.2:** в `profile.txt` у `slow_sum` два вызова, скрипт печатает `24999850000`.

## 2.10.3. Сравнение двух реализаций

Замените тело `main`, чтобы обе функции считали одну и ту же величину:

```python
def main():
    a = slow_sum(300_000)
    b = fast_sum(300_000)
    print("совпали:", a == b)
    return a
```

Снова сохраните профиль в `profile.txt`. Сравните `tottime` у `slow_sum` и `fast_sum`. `tottime` — время в самой функции, без учёта других вызовов. У формулы оно заметно меньше, чем у цикла.

**Практика 2.10.3.** В markdown перепишите две строки профиля: имя, `ncalls`, `tottime`. Отметьте, какая реализация быстрее на этом запуске.

**Критерий 2.10.3:** скрипт печатает `совпали: True`. У `slow_sum` время в `tottime` больше, чем у `fast_sum`.

## 2.10.4. timeit

`timeit` повторяет один маленький фрагмент много раз и возвращает суммарные секунды. Так сравнивают короткие выражения, не запуская полный профиль.

**Ячейка:**

```python
import timeit

loop = timeit.timeit("sum(range(10_000))", number=500)
formula = timeit.timeit("n * (n - 1) // 2", number=500, setup="n = 10_000")
print("sum(range):", loop)
print("формула:", formula)
print("цикл медленнее в", round(loop / formula, 1), "раз")
```

Числа от запуска к запуску немного меняются. Вывод «формула быстрее» должен сохраняться.

**Практика 2.10.4.** Повторите замер с `number=100` и с `number=500`. В markdown запишите оба отношения. Не сравнивайте абсолютные секунды разных компьютеров между собой.

**Критерий 2.10.4:** в обоих замерах формула занимает меньше времени, чем `sum(range(...))`.

## 2.10.5. Что не ускоряют вслепую

Ускорение имеет смысл там, где профиль показал заметную долю времени. Функция, которая вызвана один раз и занимает доли процента, не стоит переписывания на этом занятии.

**Практика 2.10.5.** В `profile.txt` после раздела 2.10.3 найдите строку, у которой `tottime` меньше, чем у `slow_sum`. Запишите её имя и одну фразу: почему её не переписывают первой.

**Критерий 2.10.5:** в заметке названа функция с меньшим `tottime`, чем у `slow_sum`, и сказано, что сначала меняют самую дорогую часть.

## 2.10.6. Профилировщики баз данных

`cProfile` видит функции Python. Если время уходит на ожидание ответа PostgreSQL, в профиле Python будет вызов драйвера, но не будет видно, какой запрос долгий и какой план выбрал сервер. Это смотрит профилировщик самой базы.

| Вопрос | Куда смотреть |
|--------|----------------|
| Какой план у одного запроса и сколько он занял | `EXPLAIN` и `EXPLAIN ANALYZE` в PostgreSQL |
| Какие тексты запросов чаще всего выполняются и сколько суммарно длятся | расширение `pg_stat_statements` |
| Какие запросы дольше заданного порога | журнал медленных запросов, параметр `log_min_duration_statement` |
| Тот же план без отдельной консоли | план запроса в DBeaver |

`EXPLAIN` показывает намерение планировщика: последовательный просмотр таблицы, поиск по индексу, соединение таблиц, оценка числа строк. `EXPLAIN ANALYZE` выполняет запрос и добавляет фактическое время и фактическое число строк. Им пользуются на копии данных или на запросе, который допустимо выполнить ещё раз.

`pg_stat_statements` копит статистику по уже прошедшим запросам: число вызовов, общее и среднее время. По нему выбирают, какой текст разбирать через `EXPLAIN` в первую очередь. Это тот же принцип, что и у `cProfile`: сначала самая дорогая часть, а не первый попавшийся запрос.

Профилировщик базы не заменяет индекс и не переписывает запрос сам. Он отвечает, где сервер тратит время. Правку текста запроса и структуры таблиц делают отдельно, уже глядя на план.

**Практика 2.10.6.** В ноутбуке тремя фразами запишите, чем `cProfile`, `EXPLAIN ANALYZE` и `pg_stat_statements` отличаются по объекту измерения: функция Python, один запрос, поток запросов на сервере.

**Критерий 2.10.6:** в заметке три разных объекта измерения, и для долгого запроса назван `EXPLAIN ANALYZE`, а не `cProfile`.

### Типовые ошибки

| Симптом | Что проверить |
|---------|----------------|
| `profile.txt` пустой или в неожиданной кодировке | Перенаправление сделано из PowerShell в корне курса; откройте файл в VS Code как UTF-8 |
