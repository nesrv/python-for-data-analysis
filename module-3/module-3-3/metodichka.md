## 3.3.1. Перечисление и домен

Перечисление — тип с фиксированным списком подписей. Домен — уже существующий тип плюс проверка. Оба создаются один раз и дальше используются как обычные типы столбцов.

```sql
CREATE TYPE channel_kind AS ENUM ('search', 'ads', 'email');

CREATE DOMAIN positive_score AS integer
    CHECK (VALUE > 0);
```

```sql
CREATE TABLE attempts (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    channel channel_kind NOT NULL,
    score positive_score
);

INSERT INTO attempts (name, channel, score)
VALUES ('Анна', 'search', 18), ('Борис', 'ads', 15);
```

Значение вне списка, например `'визит'`, сервер не примет. Балл `0` не пройдёт проверку домена.

**Практика 3.3.1.** Вставьте строку с баллом `-1` и запишите текст ошибки. Затем вставьте Веру с каналом `email` и баллом `20`.

**Критерий 3.3.1:** отрицательный балл отклонён проверкой `positive_score`. В таблице три строки, у Веры канал `email`.

## 3.3.2. Диапазон

Диапазонный тип хранит промежуток, а не два отдельных поля. `int4range` — диапазон целых. Оператор `&&` истинен, когда промежутки пересекаются.

```sql
CREATE TABLE labs (
    room text,
    seats int4range
);

INSERT INTO labs (room, seats)
VALUES ('A-1', int4range(10, 20, '[)')), ('B-2', int4range(18, 30, '[)'));

SELECT room FROM labs WHERE seats && int4range(15, 19, '[)');
```

Граница `[)` включает левый конец и не включает правый. Оба кабинета попадают в выборку: у `A-1` места до 19, у `B-2` места начинаются с 18.

**Критерий 3.3.2:** запрос с пересечением возвращает `A-1` и `B-2`.

## 3.3.3. JSONB

`jsonb` хранит документ, у которого набор полей задаёт сам документ, а не таблица. В отличие от `json`, значение разобрано и его можно индексировать. Оператор `->` достаёт вложенный фрагмент как `jsonb`, `->>` — как текст.

```sql
CREATE TABLE submissions (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL
);

INSERT INTO submissions (payload) VALUES
('{"name": "Анна", "score": 18, "tags": ["домашняя", "вовремя"]}'),
('{"name": "Глеб", "score": 11, "tags": ["домашняя"]}');
```

```sql
SELECT payload->>'name' AS name,
       (payload->>'score')::integer AS score
FROM submissions
WHERE payload @> '{"tags": ["вовремя"]}';
```

`@>` проверяет, что в документе есть указанный фрагмент. Здесь останется только Анна.

**Практика 3.3.3.** Добавьте документ Бориса с баллом 15 и меткой `"вовремя"`. Повторите запрос. Достаньте первую метку Анны выражением `payload->'tags'->>0`.

**Критерий 3.3.3:** выборка по метке `"вовремя"` содержит Анну и Бориса. Первая метка Анны — `домашняя`.

## 3.3.4. Дерево списком смежности

В списке смежности у строки есть ссылка на родителя. Корень узнают по пустому `parent_id`. Прямые дети — один фильтр. Все потомки — рекурсивный общий табличный запрос: сначала выбранный узел, затем строки, чей родитель уже попал в выборку.

```sql
CREATE TABLE categories (
    id integer PRIMARY KEY,
    name text NOT NULL,
    parent_id integer REFERENCES categories (id)
);

INSERT INTO categories (id, name, parent_id) VALUES
    (1, 'Анализ', NULL),
    (2, 'Базы', NULL),
    (3, 'Таблицы', 2),
    (4, 'Документы', 2),
    (5, 'JSON', 4);
```

```sql
SELECT id, name FROM categories WHERE parent_id = 2;

WITH RECURSIVE branch AS (
    SELECT id, name, parent_id
    FROM categories
    WHERE id = 2
    UNION ALL
    SELECT c.id, c.name, c.parent_id
    FROM categories AS c
    JOIN branch AS b ON c.parent_id = b.id
)
SELECT id, name, parent_id FROM branch ORDER BY id;
```

Первый запрос возвращает «Таблицы» и «Документы». Рекурсивный добавляет корень «Базы» и лист «JSON».

**Практика 3.3.4.** Тем же приёмом получите предков узла `5`: начните с него и на каждом шаге подключайте строку, чей `id` равен `parent_id` уже найденной строки. В итоге должны быть JSON, Документы и Базы.

**Критерий 3.3.4:** потомки «Базы» — четыре строки с номерами 2, 3, 4 и 5. Предки «JSON» — три строки: JSON, Документы, Базы.

## 3.3.5. Другие способы хранить дерево

Список смежности проще всего менять: новый ребёнок — одна вставка. Чтение всего поддерева требует рекурсии. Другие схемы переносят работу на запись.

| Схема | Как устроена | Когда уместна |
|-------|----------------|----------------|
| Список смежности | поле `parent_id` | дерево часто меняется, обходы не самые глубокие |
| Материализованный путь | в строке записан путь от корня, например `2.4.5` | нужно быстро найти потомков по префиксу пути; в PostgreSQL для этого есть тип `ltree` |
| Вложенные множества | у узла левая и правая границы обхода | потомки — один диапазон границ; вставка в середину переписывает границы соседей |
| Таблица замыканий | отдельная таблица пар «предок, потомок» | предки и потомки ищутся соединением, каждую вставку сопровождают несколькими строками связи |

В занятии остаётся список смежности из раздела 3.3.4. Остальные схемы не создавайте: в markdown запишите, какая из них неудобна при частой вставке узла в середину.

**Критерий 3.3.5:** в ответе названы вложенные множества и сказано, что вставка сдвигает границы.

## 3.3.6. Материализованное представление

Обычное представление каждый раз заново выполняет запрос. Материализованное сохраняет результат на диск. После новых строк в таблице снимок сам не меняется: его обновляют командой `REFRESH MATERIALIZED VIEW`.

```sql
CREATE MATERIALIZED VIEW category_size AS
SELECT parent_id, count(*) AS children
FROM categories
WHERE parent_id IS NOT NULL
GROUP BY parent_id
WITH DATA;

SELECT * FROM category_size ORDER BY parent_id;
```

У родителя 2 два прямых ребёнка, у родителя 4 — один.

```sql
INSERT INTO categories (id, name, parent_id) VALUES (6, 'Индексы', 2);
SELECT * FROM category_size WHERE parent_id = 2;

REFRESH MATERIALIZED VIEW category_size;
SELECT * FROM category_size WHERE parent_id = 2;
```

До обновления у «Базы» по-прежнему 2 ребёнка. После `REFRESH` счётчик становится 3.

**Практика 3.3.6.** Создайте индекс по `parent_id` на `category_size`. В markdown одной фразой запишите, чем этот объект отличается от обычного `VIEW`.

**Критерий 3.3.6:** до обновления счётчик равен 2, после — 3. В ответе сказано, что материализованное представление хранит результат, а не только текст запроса.

## 3.3.8. Практика. Типы и иерархия

Практика на один академический час. Двенадцать заданий идут по одному отделу: сначала свои типы для сотрудника, затем дерево отделов списком смежности. Текст дописывайте в `module-3-3/sql/types-tree.sql`.

Перед повторным запуском снимите объекты практики:

```sql
DROP TABLE IF EXISTS staff;
DROP TABLE IF EXISTS units;
DROP TYPE IF EXISTS person_name;
DROP DOMAIN IF EXISTS work_hours;
DROP TYPE IF EXISTS employment;
```

**Задание 1.** Создайте перечисление `employment` со значениями `'full'`, `'part'`, `'contract'`.

**Решение.**

```sql
CREATE TYPE employment AS ENUM ('full', 'part', 'contract');
```

**Задание 2.** Создайте домен `work_hours` как `numeric(4, 1)` с проверкой: значение больше 0 и не больше 40.

**Решение.**

```sql
CREATE DOMAIN work_hours AS numeric(4, 1)
    CHECK (VALUE > 0 AND VALUE <= 40);
```

**Задание 3.** Создайте составной тип `person_name` с полями `last_name text` и `first_name text`.

**Решение.**

```sql
CREATE TYPE person_name AS (
    last_name text,
    first_name text
);
```

**Задание 4.** Таблица `units`: `id`, `title`, `parent_id` со ссылкой на `units(id)`. Таблица `staff`: имя типа `person_name`, занятость типа `employment`, часы типа `work_hours`, внешний ключ `unit_id` на `units`.

**Решение.**

```sql
CREATE TABLE units (
    id integer PRIMARY KEY,
    title text NOT NULL,
    parent_id integer REFERENCES units (id)
);

CREATE TABLE staff (
    id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name person_name NOT NULL,
    kind employment NOT NULL,
    hours work_hours NOT NULL,
    unit_id integer NOT NULL REFERENCES units (id)
);
```

**Задание 5.** Вставьте дерево: `1` «Компания» без родителя, `2` «Аналитика» и `3` «Данные» — дети компании, `4` «Витрины» — ребёнок «Данных».

**Решение.**

```sql
INSERT INTO units (id, title, parent_id) VALUES
    (1, 'Компания', NULL),
    (2, 'Аналитика', 1),
    (3, 'Данные', 1),
    (4, 'Витрины', 3);
```

**Задание 6.** Добавьте двух сотрудников отдела «Витрины»: `('Соколова', 'Анна')`, занятость `full`, 40 часов и `('Ильин', 'Пётр')`, занятость `part`, 20 часов. Поле составного типа передайте конструктором `ROW`.

**Решение.**

```sql
INSERT INTO staff (full_name, kind, hours, unit_id) VALUES
    (ROW('Соколова', 'Анна'), 'full', 40, 4),
    (ROW('Ильин', 'Пётр'), 'part', 20, 4);
```

**Задание 7.** Покажите прямых детей «Компании»: только `id` и `title`.

**Решение.**

```sql
SELECT id, title
FROM units
WHERE parent_id = 1;
```

**Задание 8.** Рекурсивным запросом получите узел «Данные» и всех его потомков. В выборке две строки: «Данные» и «Витрины».

**Решение.**

```sql
WITH RECURSIVE branch AS (
    SELECT id, title, parent_id
    FROM units
    WHERE id = 3
    UNION ALL
    SELECT u.id, u.title, u.parent_id
    FROM units AS u
    JOIN branch AS b ON u.parent_id = b.id
)
SELECT id, title, parent_id
FROM branch
ORDER BY id;
```

**Задание 9.** Тем же приёмом получите предков «Витрин», включая сам узел: Витрины, Данные, Компания.

**Решение.**

```sql
WITH RECURSIVE up AS (
    SELECT id, title, parent_id
    FROM units
    WHERE id = 4
    UNION ALL
    SELECT u.id, u.title, u.parent_id
    FROM units AS u
    JOIN up ON u.id = up.parent_id
)
SELECT id, title
FROM up;
```

**Задание 10.** Постройте подписи с уровнем. У «Компании» уровень 0, у её детей 1, у «Витрин» 2. Выведите `title` и `level`.

**Решение.**

```sql
WITH RECURSIVE tree AS (
    SELECT id, title, parent_id, 0 AS level
    FROM units
    WHERE parent_id IS NULL
    UNION ALL
    SELECT u.id, u.title, u.parent_id, tree.level + 1
    FROM units AS u
    JOIN tree ON u.parent_id = tree.id
)
SELECT title, level
FROM tree
ORDER BY level, id;
```

**Задание 11.** Добавьте столбец `path text` и заполните путь от корня через точку: компания `1`, аналитика `1.2`, данные `1.3`, витрины `1.3.4`. Найдите потомков «Данных» по префиксу пути `1.3`.

**Решение.**

```sql
ALTER TABLE units ADD COLUMN path text;

UPDATE units SET path = '1' WHERE id = 1;
UPDATE units SET path = '1.2' WHERE id = 2;
UPDATE units SET path = '1.3' WHERE id = 3;
UPDATE units SET path = '1.3.4' WHERE id = 4;

SELECT id, title
FROM units
WHERE path = '1.3' OR path LIKE '1.3.%'
ORDER BY id;
```

**Задание 12.** В конец файла тремя фразами ответьте: что запретил домен `work_hours`, чем список смежности в заданиях 7–10 отличается от пути в задании 11, почему вложенные множества неудобны при вставке отдела в середину дерева.

**Решение.**

Домен не пускает 0 часов и значение больше 40. Список смежности хранит только родителя, а всё поддерево собирает рекурсия. Путь хранит цепочку в строке, и потомки ищутся по префиксу без рекурсии. Во вложенных множествах вставка в середину переписывает границы соседних узлов.

**Критерий 3.3.8:** занятость вне списка и часы `0` или `41` отклоняются. Прямые дети компании — «Аналитика» и «Данные». Предки витрин — три узла. У витрин уровень 2. По пути `1.3` находятся «Данные» и «Витрины».

### Типовые ошибки

| Симптом | Что проверить |
|---------|----------------|
| `type "channel_kind" already exists` | Тип уже создан в прошлый раз. Повторите урок на чистой базе или удалите объекты этого файла |
| `invalid input value for enum` | В списке нет такой подписи. Регистр важен: `email`, не `Email` |
| `malformed array literal` или ошибка JSON | Документ передают одной строкой в одинарных кавычках, внутренние кавычки двойные |
| Рекурсия не заканчивается | В `JOIN` родитель ищется как `c.parent_id = b.id`, а не наоборот |
| Счётчик не вырос после `INSERT` | Не выполнен `REFRESH MATERIALIZED VIEW` |
| `VIEW` путают со снимком | Обычное представление не хранит строки и не требует `REFRESH` |

После занятия слушатель ограничивает столбец своим типом или доменом, читает поле из `jsonb`, собирает поддерево рекурсией и отличает снимок материализованного представления от запроса, который считается заново.
